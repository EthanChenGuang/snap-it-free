# Summary 261026-3w6: structured Stripe route errors, signed-in locked card

## What changed

- **`lib/stripe/route-errors.ts` (new).**
  - `logStripeRouteError(tag, error)` logs one line, `[stripe] <tag> failed {type, code, message}`. It redacts `sk_/rk_/pk_ (test|live)` and `whsec_` tokens and never logs the error object, request or headers.
  - `stripeRouteError(tag, error)` answers 502 `{error:'stripe_error'}` for `Stripe.errors.StripeError` and 500 `{error:'internal_error'}` for anything else.
- **`POST /api/stripe/checkout` and `POST /api/stripe/portal`.** Everything after the 503 guard sits in a try/catch that uses the helper. Contracts are unchanged: 503 payments_disabled, 401, 400, 404, 409 and 502 checkout_unavailable.
- **`GET /api/stripe/checkout/return`.** `requireAuth()` moved inside the try, so an auth failure now redirects to `?checkout=pending` instead of an empty 500. It logs through the same helper.
- **Locked card (`components/onboarding/LockedViews.tsx`).** "Already subscribed?" is now `AccountPrompt`.
  - A guest still gets the "Sign in" link to `/settings`.
  - A signed-in user gets a **"Refresh status"** button. It calls `checkRestore()` (`GET /api/subscription`) and reloads if active. Otherwise it shows `locked.refreshNothing`.
  - Nothing renders while `useAuthSession()` is loading.
  - New copy: `locked.refreshStatus` and `locked.refreshNothing` (en/it/zh).
- **Paywall and Settings.** They already showed localized `paywall.checkoutError` and `subscription.portalError` on any non-2xx, which component tests now prove. Added `data-testid` (`paywall-checkout-error`, `settings-portal-error`) and `role="alert"` on the portal error.
- **Tests.**
  - 6 route tests: 502 JSON with no key in the body or log; a key inside a Stripe message is redacted; 500 on unexpected; the same for the portal; return redirects pending.
  - Component tests via react-dom + jsdom (no new dependency, `components/test/render.tsx`): paywall error in en/it/zh plus retry, Settings portal error in en/it/zh, locked card for a guest, signed in (feed, detail, favorites; en/it/zh), refresh with nothing active, and loading.
  - `vitest.config.ts` now includes `components/**/*.test.tsx`.
- **Verify skill.** The `onboarding` journey stubs `/api/stripe/checkout` with a 502 (`page.route`), asserts the alert and an enabled CTA, then retries into coming soon. It also asserts the guest sign-in link on the locked feed. `features/paywall.md` documents `lock-account` and `stripe-errors`.

## Finding

The client side was not actually silent. `checkoutOutcome` already mapped an empty 500 (where `res.json()` fails) to the error state. The real defects were on the server: an empty 500 body, an unstructured Next error dump instead of a tagged line, and the return route's unguarded `requireAuth()`.
