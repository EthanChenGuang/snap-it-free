# Quick Task: Fix invisible black-on-black text on selected filter chips (app-wide)

Selected/active chips (map zone filter, list category filter) render with a
black background and invisible black text. User confirms this is a shared
pattern, not a one-off — must be fixed at the source, everywhere it appears.

## Root cause (verified)

**Not a missing class or wrong token.** `CategoryFilterChips`, `ZoneFilterChips`,
and `ZoneChipSelector` all correctly render `variant="chipActive"` on the
shared `components/ui/button.tsx`, whose `buttonVariants` (cva) definition is
already correct:

```
chipActive: 'bg-primary text-on-primary border border-primary'
```

And `app/globals.css` already defines a correct, contrast-safe token pair:
`--color-primary: #000000` / `--color-on-primary: #ffffff` (light),
`--color-primary: #e5e2e1` / `--color-on-primary: #1c1b1b` (dark).

The bug is in `lib/utils.ts`'s `cn()` — it pipes every class string through
`twMerge()` (tailwind-merge) with **default config**, which has no knowledge
of this app's custom `@theme` font-size scale (`text-h1`, `text-h2`, `text-h3`,
`text-body-lg`, `text-body-md`, `text-label-md`, `text-label-sm`, defined in
`app/globals.css`). tailwind-merge falls back to pattern-matching any
`text-{word}` class it doesn't recognize as a "text-color" utility — so
`text-label-sm` (a **font-size** class, added by `size="sm"`) is misclassified
into the same conflict group as `text-on-primary` (the real color class, added
by `variant="chipActive"`). Because `size`'s classes are concatenated *after*
`variant`'s in `buttonVariants`, tailwind-merge keeps the later class
(`text-label-sm`) and **silently deletes** `text-on-primary`. Text then
inherits color from an ancestor (near-black `on-background`/`on-surface`),
landing invisible on the black `bg-primary` chip.

Confirmed by reproducing the exact class string `buttonVariants` produces for
`variant="chipActive" size="sm"` through the real `twMerge` import:

```
node -e "
const { twMerge } = require('tailwind-merge');
console.log(twMerge(
  'text-label-md',
  'bg-primary text-on-primary border border-primary',
  'h-8 px-space-sm text-label-sm',
).includes('text-on-primary'));
"
# → false
```

This is app-wide by construction: `cn()` is imported in 26 files, and
`components/ui/button.tsx` is the **only** `cva()`-based variant component in
the app. Every current chip built on `variant="chipActive"` + `size="sm"`
(`CategoryFilterChips` on the list page, `ZoneFilterChips` on the map explorer
and Favorites page, `ZoneChipSelector` on Settings) hits this, and any future
chip/button variant that pairs a custom font-size token with a color token
through `cn()` would hit it too. The inactive/unselected chip variant
(`text-on-surface` on `bg-surface`) has the *same* underlying bug but goes
unnoticed because the inherited fallback color happens to already be dark —
i.e. it "looks right" for the wrong reason. Fixing the merge config fixes both
paths correctly, everywhere, for good.

## Tasks

### Task 1: Register the custom font-size scale with tailwind-merge

- **files:** `lib/utils.ts`
- **action:** Replace the plain `twMerge` import with `extendTailwindMerge` from
  `tailwind-merge`, configured with `extend.theme.text: ['h1', 'h2', 'h3',
  'body-lg', 'body-md', 'label-md', 'label-sm']` — the exact custom `--text-*`
  scale keys defined in `app/globals.css`'s `@theme` block (minus the `text-`
  prefix, per tailwind-merge's `extendTailwindMerge` theme-extension API).
  Keep `cn()`'s signature and behavior identical for every other call site;
  this only teaches the merge engine that these particular `text-*` classes
  are font-size utilities, not color utilities, so it stops grouping them
  against real `text-on-*` / `text-black` / `text-white` color classes. Do not
  touch `components/ui/button.tsx`, `CategoryFilterChips.tsx`,
  `ZoneFilterChips.tsx`, or `ZoneChipSelector.tsx` — none of them need to
  change; the bug is entirely in the shared merge config they all route
  through.
- **verify:** `npm run lint` (runs `tsc --noEmit`) passes with zero errors —
  confirms the `extendTailwindMerge` config and updated import compile cleanly.
  Behavioral proof that the merge output is actually correct is the regression
  test added in Task 2.
- **done:** `lib/utils.ts` exports the same `cn(...)` signature, now backed by
  an `extendTailwindMerge` instance that knows the app's custom font-size scale.

### Task 2: Add a regression test locking in the fix

- **files:** `lib/utils.test.ts` (new)
- **action:** Add a Vitest suite for `cn()` covering exactly the shape
  `buttonVariants` produces (base classes with `text-label-md`, then a variant
  string containing a `text-on-*` color class, then a `size="sm"` string
  containing `text-label-sm`) for both the active chip (`text-on-primary`) and
  inactive chip (`text-on-surface`) cases, asserting the color class survives
  the merge. Also add one assertion that a genuine same-scale conflict still
  resolves correctly (`cn('text-label-md', 'text-label-sm')` keeps only
  `text-label-sm`), and one unrelated sanity check that ordinary Tailwind
  conflict resolution (e.g. `px-2 px-4` -> `px-4`) is unaffected by the
  `extendTailwindMerge` config change.
- **verify:** `npx vitest run lib/utils.test.ts` — all assertions pass.
- **done:** Regression test exists and passes; running it against the
  pre-fix `lib/utils.ts` (temporarily reverting Task 1) fails on the
  `text-on-primary`/`text-on-surface` assertions, confirming the test
  actually catches this bug.
