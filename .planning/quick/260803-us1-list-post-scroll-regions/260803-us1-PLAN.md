# Quick Task: Elenco list scroll region too small; Pubblica does not scroll

Two reported symptoms on mobile (via ngrok tunnel):

1. **Elenco (`/list`)** — the scrollable item list is confined to an inappropriately short region.
2. **Pubblica (`/post`)** — the page does not scroll at all.

Both are the same root cause in the shared app shell.

## Diagnosis (completed before planning)

Measured with headless Chromium at 390×844, iPhone UA (`/tmp/scrollprobe.mjs`).

### The shell reserves header/nav space with hardcoded constants that are both wrong

`app/globals.css:99-107`

```css
:root {
  --shell-header-height: 57px;
  --shell-bottom-nav-height: 64px;
}
.app-main {
  height: calc(100dvh - var(--shell-header-height) - var(--shell-bottom-nav-height));
  margin-top: var(--shell-header-height);
}
```

`Header` (`components/shell/Header.tsx:17`) and `BottomNav` (`components/shell/BottomNav.tsx:25`)
are both `position: fixed`, so CSS cannot know their real size. Measured reality:

| Constant | Declared | Actual measured | Consequence |
|---|---|---|---|
| `--shell-header-height` | 57px | **77px** | `.app-main` starts 20px too high — its first 20px sit *behind* the fixed header |
| `--shell-bottom-nav-height` | 64px | **71.1px** | `.app-main` ends at y=780 while the nav starts at y=772.9 — 7.1px sits *behind* the nav |

So the shell's content box is misaligned at both ends on every route.

### `.app-main` has `overflow: visible` inside `body { overflow: hidden }`

`app/layout.tsx:31` sets `overflow-hidden` on `<body>`. Per the html/body overflow-propagation
rule, that value propagates to the viewport, so **the document itself cannot be scrolled by the
user**. `.app-main` is a fixed-height box with the default `overflow: visible`, so any content
taller than it is painted outside the box and then clipped by the viewport — unreachable.

The result: a route only scrolls if its own page component happens to declare an internal
`overflow-y-auto`. Some do, some don't.

| Route | Root classes | Owns a scroller? |
|---|---|---|
| `/` map | `map-container ... overflow-hidden` (`height: 100%`) | n/a — fits exactly, correct |
| `/list` | `flex h-full flex-col overflow-hidden pb-24` | yes (`ListingFeed` inner div) |
| `/post` | `mx-auto flex h-full ... pb-28` | **no** |
| `/post/manage` | `mx-auto flex h-full ... pb-28` | **no** |
| `/settings` | `mx-auto flex h-full ... pb-28` | **no** |
| `/favorites` | `flex h-full flex-col overflow-hidden pb-24` | yes (`ListingFeed` inner div) |
| `/listing/[id]` | `flex h-full flex-col overflow-y-auto` | yes |

### Symptom 1 — `/list`: the `pb-24` double-reserves the nav

`.app-main` already subtracts the bottom-nav height. `ListPageClient` (`components/listings/ListPageClient.tsx:35`)
then adds `pb-24` (96px) *inside* that already-shortened `overflow-hidden` box, so the inner
`ListingFeed` scroller (`components/listings/ListingFeed.tsx:30`) loses another 96px.

Measured `/list` scrollport: `top: 250, bottom: 684, clientHeight: 434` — while the nav does not
begin until **y=772.9**. That is **~89px of dead, unusable space** below the list, on top of the
20px stolen at the header. The list gets 434px of the ~696px actually available — **62%**.

This is the reported "limited to an area that is not appropriate".

### Symptom 2 — `/post`: no scroller exists anywhere

`PostPageClient` (`components/ugc/PostPageClient.tsx:32`) is `h-full` (pinned to `.app-main`'s
723px) with no `overflow-y-auto`. Measured: `clientHeight 723` vs `scrollHeight 1137` →
**414px of the form is unreachable**, and since `body`'s `overflow: hidden` propagates to the
viewport, no user gesture can scroll to it. The probe confirms `document.scrollingElement`
moves only when driven programmatically. `/post/manage` and `/settings` share the identical defect.

### The Stitch prototypes agree

- `map_explorer_notion_style/code.html:108,122` — `overflow: hidden` + `height: calc(100vh - 64px - 64px)`. **Only the map** is meant to be a fixed, non-scrolling canvas.
- `listing_feed_notion_style/code.html:134` — `<body class="... min-h-screen flex flex-col pb-24">`: an ordinary document-scroll page whose `pb-24` clears the fixed nav.
- `post_free_item_notion_style/code.html:137` — `<body class="text-on-surface">`: plain document scroll, no height constraint at all.

The React port generalised the map screen's fixed-height, `overflow: hidden` model onto *every*
route, then re-applied the prototypes' `pb-24`/`pb-28` on top of a box that had already
subtracted the nav. That double reservation, plus the two wrong constants, is the whole bug.

## Fix strategy

Fix it once in the shell rather than per page. Replace the hardcoded-constant model with a
flex column, so the header and nav contribute their *real* heights and no magic numbers remain:

```css
.app-shell { display: flex; flex-direction: column; height: 100dvh; }
.app-main  { flex: 1; min-height: 0; overflow-y: auto; overflow-x: hidden; }
```

`Header`/`BottomNav` change from `fixed` to in-flow `relative shrink-0`, keeping `z-[100]` so
they still paint above the map's vaul drawer (`z-50`). The map is unaffected: `.map-container`
is `height: 100%` of a now definite-height flex child, so it fills exactly and never scrolls.

Then remove the now-double-counted `pb-24`/`pb-28` and switch the non-scrolling pages from
`h-full` to `min-h-full` so their content can exceed the viewport and `.app-main` scrolls it.

No visual tokens, colours, borders, radii or spacing scale change — layout only.
