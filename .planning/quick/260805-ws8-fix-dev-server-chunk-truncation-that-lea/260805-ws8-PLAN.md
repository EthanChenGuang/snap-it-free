# Quick Task 260805-ws8: Stop dev chunk truncation (map stuck loading / homepage hangs)

## Problem

The homepage hangs and the map sits on `地图加载中…` forever. This is the same
class of failure as quick task `260805-r3k` (commit `dc3d60e`), which mitigated it
by shrinking `app/layout.js` from 5.07 MB to 2.39 MB. It has recurred because the
mitigation only bought margin — it did not remove the trigger.

## Root cause (proven, not inferred)

Next's dev server rewrites `app/layout.js` **while it is streaming that same file**
to the browser. The response headers carry the pre-rewrite `Content-Length`, but the
read stream ends early, so the browser receives a truncated JavaScript file.

Evidence — perfect 1:1 correlation between "file rewritten during request" and
"response truncated", measured on the running dev server (port 3003):

```
run1 declared=2393626 actual=2359296 TRUNC | mtime 1785965720->1785965737 REWRITTEN
run2 declared=2393626 actual=2393626 OK   | mtime unchanged  same
run3 declared=2393626 actual=2393626 OK   | mtime unchanged  same
run4 declared=2393626 actual=2393626 OK   | mtime unchanged  same
```

Supporting evidence:

- Truncation always lands on a 64 KB read boundary (2359296 = 36 x 65536,
  2162688 = 33 x 65536) — a cut-short read, not a corrupt build.
- File size before and after the rewrite is **identical** (2393626 -> 2393626):
  webpack re-emits a byte-identical chunk. The rebuild is pure waste.
- Serving the exact same file from a plain Node `createReadStream` server returns
  the full 2393626 bytes 3/3 times. So the file, the filesystem (native ext4), and
  disk I/O are all fine — only Next's dev server truncates.
- Memory is not a factor (36 GB free, next-server at 2.3 GB RSS).

Why it recompiles: Next's `onDemandEntries` defaults to
`maxInactiveAge: 60_000` / `pagesBufferLength: 5`. An entry untouched for 60 s is
disposed, so the next request rebuilds and re-emits it — straight into the race
above. This matches the observed pattern exactly: the first request after an idle
gap truncates, and requests inside the window never do.

Failure chain: truncated `layout.js` -> `SyntaxError` -> React never hydrates ->
the `next/dynamic` `MapExplorer` in `components/map/MapHomeClient.tsx` is stuck on
its loading fallback forever -> "map loading" + hanging homepage. No error boundary
can catch this, because hydration never starts.

## Decisions (locked by user)

- **Approach:** stop the recompile churn via `onDemandEntries`. Do *not* shrink the
  root layout chunk again — that is the treadmill that already regressed once.
- **Commit scope:** stage **only** the files this task edits. The working tree holds
  ~45 unrelated modified files; they must be left untouched and uncommitted.

## Tasks

### Task 1 — Keep dev entries alive so layout.js stops being re-emitted

- **files:** `next.config.ts`
- **action:** Add an `onDemandEntries` block to `nextConfig` that keeps built pages
  in the buffer far longer than the default 60 s, so the dev server stops disposing
  and re-emitting `app/layout.js` between page loads:

  ```ts
  onDemandEntries: {
    maxInactiveAge: 60 * 60 * 1000,
    pagesBufferLength: 25,
  },
  ```

  Add a short comment recording *why* (dev-server rewrites the chunk mid-stream and
  truncates the response; see this task id). Keep it to one or two lines — match the
  existing commenting style in the file, which explains non-obvious constraints.

  Leave `devIndicators`, `allowedDevOrigins`, `images`, and the Serwist export
  exactly as they are.

- **verify:**
  1. Restart the dev server (`npm run dev`) — config changes require a restart.
  2. Load the homepage once, wait >90 s (comfortably past the old 60 s eviction
     window), then run the mtime/length correlation probe against
     `/_next/static/chunks/app/layout.js`: declared `Content-Length` must equal the
     actual byte count, and the on-disk mtime must not change across the request.
  3. Repeat the idle-then-request cycle at least 3 times. All must report `OK`.
- **done:** No truncated `layout.js` responses across repeated cold/idle loads, and
  the chunk file is no longer rewritten on request.

### Task 2 — Confirm the user-visible symptom is gone

- **files:** none (verification only)
- **action:** With the dev server restarted, load `http://localhost:3003/` in a
  browser after an idle period. Confirm the map paints instead of sitting on
  `地图加载中…`, and that the browser console shows no `SyntaxError` from
  `layout.js`.

  If a browser is unavailable, say so explicitly rather than claiming the UI works;
  fall back to asserting the full-length chunk fetch from Task 1 and report that the
  visual check was not performed.
- **verify:** Homepage renders the map; no chunk-parse `SyntaxError` in console.
- **done:** Map loads on a cold homepage visit.
