<objective>
Wave 1 tracer: wire the full end-to-end "set a pickup location for a post" capability — PostForm's tappable location row navigates to the map picker in post context (radius UI hidden, different copy), Confirm persists the draft independently of browse state and returns to PostForm, and PostForm reads the draft back to show the confirmed city and gate submit.

Purpose: prove the context-branching architecture (query-param dispatch, independent storage, conditional radius UI) end-to-end on the single riskiest new capability this phase adds, before Plan 03's browse-side polish builds on the same branch point.
Output: Working post-pickup-location round trip; PostForm no longer uses the old GPS toggle.

**Flagged planner assumption — D-12 not fully achievable this phase (surface to developer, do not silently claim done):** D-12 asks that "photo, title, etc." survive the navigate-out-and-back round trip. Verified against Next.js 16 docs (Context7 `/vercel/next.js/v16.2.9`): without the opt-in `cacheComponents` experimental flag (not enabled in this project's next.config.ts), a top-level App Router navigation between two distinct routes — `/post` and `/select-location` — fully unmounts and remounts the client component tree either way (`router.push` or `router.back()`), resetting all local `useState`, including `title`/`description`/`category`/`condition`, and `photoFile`/`photoPreview` (a `File`/object-URL cannot round-trip through JSON storage at all). CONTEXT.md's own Deferred Ideas list explicitly restricts this phase's session draft to "location fields only," which forecloses the one workaround (storing the other fields in sessionStorage too). This plan does not attempt a fix — `photoFile`/`title`/`description`/`category`/`condition` reset to defaults after the round trip, same as any other unmount. This is a real UX regression versus the pre-Phase-13 inline-toggle flow (which never navigated away) and should be raised with the developer as a candidate for a follow-up phase (e.g. lifting the non-photo fields into a persistent layout-level context, or enabling Cache Components app-wide).
</objective>
