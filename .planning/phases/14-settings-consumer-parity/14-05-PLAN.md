<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → GET/PATCH /api/user/notification-prefs | RLS restricts every read/write to the caller's own row (`user_id = auth.uid()`) |
| Cron (service role) → user_notification_prefs read | Bypasses RLS by design (service-role client), read-only in this plan |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-07 | Elevation of Privilege | GET/PATCH /api/user/notification-prefs | medium | mitigate | `requireAuth()` derives the acting user server-side; the query/upsert is additionally RLS-scoped to `user_id = auth.uid()`, so even a crafted body cannot target another user's row |
| T-14-08 | Tampering | Client-side DND bypass (editing browser state to fake "always push") | low | accept | DND is enforced entirely server-side inside the cron's `processOneEvent`; the client toggle is advisory UI state only — the DB-stored preference (fetched fresh each cron run), not any client-supplied value at push time, is authoritative |
| T-14-09 | Repudiation | Suppressed-push match visibility | medium | mitigate | The `alert_matches` upsert is unconditional and runs before the per-user DND check — a suppressed push never means a lost match; the prohibition above is the explicit gate against a future refactor accidentally moving the upsert inside the suppression branch |
| T-14-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages this plan |

</threat_model>
