<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → GET/POST /api/user/delete | `userId` always derived server-side from `requireAuth()`'s session, never from client-supplied input |
| POST /api/user/delete → deleteAccountData (service role) | Bypasses RLS by design — the one place in this codebase a client action triggers a service-role multi-table teardown |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-10 | Elevation of Privilege / IDOR | POST /api/user/delete | high | mitigate | `userId` is always `requireAuth()`'s `user.id`; the request body is never parsed for a target user — an attacker cannot delete another account by supplying a different id |
| T-14-11 | Repudiation / Tampering | Partial-delete race leaving a "half deleted" account while the client believes success | high | mitigate | `deleteAccountData`'s fixed Storage→RPC→admin.deleteUser order (Plan 14-03) with early-return-on-error; the client only calls `signOut()`/clears state/redirects after a 200 response, never optimistically |
| T-14-12 | Tampering / Information Disclosure | Active-claims count staleness understating counterparty impact | medium | mitigate | GET /api/user/delete computes the count live on every call (no caching), so the warning line reflects real-time state at confirm time |
| T-14-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages this plan |

</threat_model>
